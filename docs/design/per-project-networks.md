# Design: per-project networks

Status: implemented. Breaking change, no legacy mode. User-facing docs: README,
"Per-project networks".

Implementation notes:

- `compose-cmd.sh` takes `--project <name>` and refuses `up` without it, so no
  path can start a project without its network. The override is added after
  the guard has checked the project's own files.
- The guard tracks the top-level section of `docker compose config` output, so
  external **volumes** stay allowed while external **networks** are refused.
- The check after `up` uses Docker labels (`com.docker.compose.project`), not
  network names, to decide which networks belong to the project. It also
  allows `network_mode: container:<id>` when the target is in the same project
  (Compose's `service:` sidecars).
- `status` has a NETWORK column: `attached`, `no nginx`, `absent`, `bad name`.
- Switch-over caveat found during implementation: until a project is moved, a
  webhook redeploy or respawn of it runs `down` and then has its `up` refused,
  leaving it offline. The README tells operators to hold pushes (or deactivate
  the webhook) and avoid `rebuild-all` until each project is moved.

## Goal

Today every app container and nginx share one Docker network,
`internal_proxy_pass_network`. A compromised container in one project can open
connections to every other project's app, and can send forged
`X-Forwarded-For` / `X-Real-IP` headers that bypass nginx.

After this change, each project's app sits on a network that only it and nginx
share. Containers in different projects have no network route to each other.
nginx becomes the only bridge, and it is already the trusted entry point.

Non-goals: isolating containers inside one project from each other, or
limiting outbound internet access.

## Model

```
                 ingress-nginx
           ┌──────────┼──────────┐
     baton-dresskod   baton-shop   baton-blog      (one network per project,
           │          │            │                created and owned by baton)
     dresskod app   shop app     blog app
           │          │            │
     dresskod_default shop_default blog_default    (each project's own compose
       (db, redis…)   (db…)        (db…)            network, unchanged)
```

- Network name: `baton-<project>`, created with `--internal` (no outbound
  route; the app keeps internet access through its own default network) and
  the label `baton.project=<project>`.
- nginx reaches the app at a hostname baton chooses: `baton-<project>`, set as
  a network alias on the app service. Projects no longer pick their own alias.
- Static-only projects have no containers and get no network.

## What a project declares

Breaking change. In the project `.env`:

| Key | Change |
|---|---|
| `APP_SERVICE` | **New, required for dynamic projects.** The compose service name nginx proxies to (e.g. `django`). |
| `APP_PORT` | Unchanged. |
| `DOCKER_NETWORK_SERVICE_ALIAS` | **Removed.** Deploy fails with a clear message if it is still set, so nobody assumes it is used. |

In the project compose files: remove `internal_proxy_pass_network` and any
aliases. A project's compose no longer mentions baton's networks at all.

`APP_SERVICE` only tells baton which service to attach. It is not a hostname:
nginx never connects to it, so two projects using the same service name
(`web`, `django`…) is harmless.

In `server.conf`: `proxy_pass http://${DOCKER_NETWORK_SERVICE_ALIAS}:${APP_PORT};`
becomes `proxy_pass http://${UPSTREAM_HOST}:${APP_PORT};`. A template that
still uses the old placeholder fails at render with the existing
un-substituted placeholder check, before anything changes.

## `UPSTREAM_HOST`: where it comes from and how it resolves

**Generated by baton, from the project name.** One helper computes
`baton-<project>` from the project directory name (`/srv/projects/dresskod`
→ `baton-dresskod`). It is never read from `.env`; a `.env` that sets
`UPSTREAM_HOST` is rejected. The project name must be a DNS label (lower-case
letters, digits, `-`, starting with a letter or digit); deploy checks this.

Every consumer calls that one helper, so the values can't drift apart:

| Consumer | Use |
|---|---|
| Network helper | creates network `baton-<project>` |
| Generated compose override | sets alias `baton-<project>` on `APP_SERVICE`, on that network |
| `render-server-conf.sh` | substitutes `${UPSTREAM_HOST}` (built-in, like `SITE_KEY`) |
| `nginx-conf-allow.sh` | requires `proxy_pass` to target exactly `baton-<project>` |

**After rendering it is a fixed hostname.** The template line becomes
`proxy_pass http://baton-dresskod:8000;` in `conf.d/`. nginx never sees the
placeholder.

**Resolved by Docker's embedded DNS, when nginx loads its config.** nginx asks
`127.0.0.11` for `baton-dresskod`. Docker answers only for names on networks
nginx is attached to, and returns the `APP_SERVICE` container's address on
network `baton-dresskod`. Containers in other projects aren't on that network:
the name doesn't resolve for them and the address isn't routable from them.

nginx resolves once per load, and a recreated container gets a new address,
so nginx is reloaded after every Compose `up`. Deploy and the webhook
redeploy already do this.

The network and the alias share the string `baton-<project>`. Docker keeps
network names and DNS names in separate namespaces, so they don't clash; the
match just makes `docker network ls` and `conf.d/` easy to line up.

## How baton attaches the app: a generated compose override

`compose-cmd.sh` already passes every compose file with `-f`. It will append
one more, generated per project, always last:

```yaml
# /opt/baton-orchestrator/tmp/compose/<project>.yml (generated, do not edit)
services:
  django:                       # APP_SERVICE
    networks:
      default: {}               # keep the project's own network (see note)
      baton_ingress:
        aliases: [baton-dresskod]
networks:
  baton_ingress:
    name: baton-dresskod
    external: true
```

Note: once a service has a `networks:` key, Compose stops attaching it to
`default` implicitly, so the override must list `default` too.

Because it lives in `compose-cmd.sh`, every path that runs Compose gets it:
deploy, respawn, rebuild-all and the webhook redeploy in `handle-webhook.sh`.

## Guard rules (required: isolation fails without them)

Separate networks are not enough on their own. Today's compose guard only
rejects `network_mode: host`. A project could still:

1. **Join another project's network** by declaring `baton-shop` (or the old
   shared network) as an external network.
2. **Share another container's network stack** with
   `network_mode: container:<other>` or `service:` pointing outside the project.
3. **Hijack another project's traffic.** nginx is on every project network,
   and Docker's DNS answers for names on all of them. A project that names a
   service, `container_name`, `hostname` or alias `baton-shop` would compete
   for shop's hostname.

Rules:

- Reject any external network in project compose files. Only baton's override
  may add one.
- Reject `network_mode: host`, `bridge` (Docker's default bridge is shared by
  every container on it) and `container:*`. `service:*` stays allowed:
  Compose only accepts services of the same project there. `none` stays
  allowed; it only removes the container's own networking.
- Reserve the `baton-` prefix: reject service names, `container_name`,
  `hostname` and aliases starting with it in project files.
- Check the real state after `up`, not only the config text: inspect each of
  the project's containers and confirm it is attached only to
  `<compose project>_*` networks and its own `baton-<project>`. On a
  violation, bring the project down and fail the deploy. The current guard is
  a line scan; it can't parse YAML reliably, so the check after `up` is the
  one to trust.
- `nginx-conf-allow.sh`: `proxy_pass` must target `baton-<project>`, the
  computed host, instead of the alias read from `.env`.

## Lifecycle

| Step | What happens |
|---|---|
| `deploy` (dynamic) | Ensure network `baton-<project>` exists (create if missing). Ensure nginx is connected (`docker network connect`, skipped if already attached). Then the existing steps: render, Compose up with the override, nginx test and reload. nginx must be attached before the test, or it can't resolve `baton-<project>`. |
| Webhook redeploy | Same ensure step before Compose `up`, then reload (already done today). |
| `stand-down` | In this order: containers down; vhost removed, nginx tested and reloaded (both as today); disconnect nginx and `docker network rm baton-<project>`; regenerate the orchestrator network list. If the network can't be removed (something outside baton still attached), warn and continue: the project is already down, and `status` shows the leftover. `respawn` therefore recreates the network every time, which is cheap. |
| `remove-project` | Nothing extra: stand-down already removed the network. |
| `orchestrator-respawn` | Recreating nginx drops connections made with `docker network connect`. nginx would then fail to **start** (unknown upstream host in `conf.d`). Fix: baton keeps a generated `orchestrator/docker-compose.networks.yml` listing every `baton-*` network as external, and respawn passes it with `-f`. A recreated nginx is attached at creation, before it starts. Deploy and stand-down regenerate the file. A stale entry for a deleted network would make nginx fail to be created, taking every site down, so the file must always match the networks that exist. |
| Host reboot | No action: containers are restarted, not recreated, and keep their networks. |
| `setup.sh` | Stop creating `internal_proxy_pass_network`. Check Docker's address pools and warn (see below). |
| `cleanup.sh` | Remove `baton-*` networks instead of the shared one. |
| `status` | Show per project: network present, nginx attached. |

The ensure step lives in `tools/helpers/project-network.sh` and runs inside
`compose-cmd.sh` before every `up`. Deploy (through `restart-containers.sh`)
and the webhook redeploy both go through it, and `compose-cmd.sh` refuses `up`
without `--project`, so no path can skip it.

## Docker network limit

Each dynamic project now uses two networks: baton's, plus its own compose
default. Docker's default address pools hold about 31 networks in total, so a
VPS tops out around **14 projects** with default settings.

This is a setting, not a hard limit. In `/etc/docker/daemon.json`:

```json
{ "default-address-pools": [ { "base": "10.200.0.0/16", "size": 24 } ] }
```

This gives 256 networks of 254 addresses each. It takes effect after
`systemctl restart docker`, which stops every container for a moment, so do
it during setup or in a maintenance window. Existing networks keep their
subnets. Choose a base range that doesn't overlap the VPS or provider network.

`setup.sh` warns, with the snippet, when `/etc/docker/daemon.json` has no
`default-address-pools`; the README documents the setting. Don't edit `daemon.json` automatically: restarting Docker is
disruptive and the range choice depends on the host.

## Switch-over procedure

No legacy code is needed if the steps run in this order. The running nginx
keeps its old attachments until it is recreated, so the old shared network
stays usable during the move without any code supporting it.

1. Before starting: set `default-address-pools` if you'll have more than about
   a dozen projects.
2. Pull the new baton into `/opt/baton-orchestrator`. **Do not** respawn the
   orchestrator yet.
3. For each project: edit compose (drop `internal_proxy_pass_network` and the
   alias), `.env` (add `APP_SERVICE`, drop `DOCKER_NETWORK_SERVICE_ALIAS`) and
   `server.conf` (`UPSTREAM_HOST`). Then `baton respawn <project>`. The project
   moves to its own network while the others keep working.
4. When all projects are moved: `baton orchestrator-respawn`. nginx is recreated
   attached only to `baton-*` networks.
5. `docker network rm internal_proxy_pass_network`.
6. Check: `baton status`, and from one app container try to reach another
   project's `baton-<project>:<port>`; it must fail.

Rollback: before step 4, `git checkout` the previous baton and respawn the
moved projects with their old compose files. After step 4, recreate the shared
network and respawn everything on the old version.

## Tests

- Unit (`tests/`, no Docker): override generation (service, alias, network
  name), project-name validation for network names, guard rules (external
  network, `network_mode`, `baton-` prefix), `proxy_pass` check with the
  computed host, `UPSTREAM_HOST` rendering.
- Integration (real Docker; staging VPS or a local Docker host). **Not run
  yet**: the unit tests use a Docker stub. Run before migrating production:
  two projects
  deployed; each reachable through nginx; no route between them; nginx
  survives `orchestrator-respawn`; the webhook redeploy keeps the network;
  `remove-project` deletes it; a project declaring `baton-<other>` is refused.

## Effect on recent work

- `SERVER_CONF_EXTRA_VARS` keeps working unchanged. Add `UPSTREAM_HOST` and
  `APP_SERVICE` to its reserved names.
- dresskod's shared proxy secret becomes mostly redundant once only dresskod
  and nginx share its network. Dropping it is a dresskod decision (template
  and app together), independent of this work.

## Known limits

- nginx resolves each upstream when it loads its config. If one project's app
  is down at reload time, the whole reload fails. That's true today as well.
  Lazy resolution (`resolver` plus a variable in `proxy_pass`) would fix it,
  but the config allowlist forbids variables in `proxy_pass`. Out of scope
  here.
- Containers inside one project still reach each other freely. That's the
  project's own concern.

## Decisions

Settled:

1. **`APP_SERVICE` is a required `.env` key** for dynamic projects. No default
   service name for now; deploy fails with a clear message when it is missing
   or names a service that doesn't exist in the compose files.
2. **The placeholder is renamed to `${UPSTREAM_HOST}`**, computed by baton as
   described above. `DOCKER_NETWORK_SERVICE_ALIAS` is removed from `.env`,
   templates, docs and examples.

3. **Project networks are `--internal`.** They carry nginx-to-app traffic
   only. Apps keep internet access through their own compose default network,
   which the generated override always keeps attached.
4. **The network is deleted on stand-down** and recreated on deploy. It costs
   nothing to recreate and leaves no stale networks behind.
